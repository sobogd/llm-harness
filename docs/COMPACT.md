# Компакт: авто на границе токенов + ручной

## Принципы

1. **Источник правды — реальный `usage.prompt_tokens`** из стрима
   (`stream_options: {include_usage: true}`), а не оценка `chars/4`.
   mtplx честно считает токены; в request-log это `prompt_tokens`.
2. **Граница — выставленная настройка, не окно модели.**
   Модель держит 64 000; мы выставляем `max_context_tokens` (дефолт 60 000)
   и компактуем, когда реальное потребление доходит до неё. Расчёт строится
   на том, что модель выдержит чуть больше выставленного — значит можно
   триггерить компакт **на границе**, а не «на всякий случай» на 50%.
3. **Одним компактом не ограничиваемся**: если после свёртки следующее
   `usage` снова выше границы — срабатывает повторно. Каждый компакт
   **обновляет роущий бриф** (структурированное резюме, которое живёт в
   истории и переносится в следующий компакт без потери — см. ниже),
   поэтому история сжимается монотонно, а суть задачи сохраняется.

## Границы и условия

Обозначения: `P` — `usage.prompt_tokens` последнего запроса,
`B` — `Settings.max_context_tokens`, `O` — `Settings.max_output_tokens`,
`W` — контекст сервера (204 800, см. MTPLX.md), `H` — запас (2 048).

Инвариант всегда: `B + O ≤ W − H` (проверяется в SetSettings).

| Условие | Действие |
|---|---|
| `P + O > B` (до следующего LLM-запроса) | **автокомпакт**, затем запрос уходит |
| `P > W` (переполнение, не должно случиться по инварианту) | форс-компакт с `keep_last_messages = 4`, повтор запроса; если не помогло — `CONTEXT_OVERFLOW` |
| `finish_reason == "length"` | выход уперся в `O`: один «продолжи с места остановки» (без компакта); повторный `length` подряд — `O` считается слишком малым, сообщаем `error` с советом поднять `max_output_tokens` |
| ручной `Compact` по gRPC | компакт вне условий: сразу (или после текущего turn'а, если ран идёт) |

Почему `P + O > B`, а не `P > B`: новый ответ ещё не добавлен, но займёт
место. Это и есть «граница токенов»: компакт срабатывает ровно в момент,
когда следующий full-размерный ответ не влезает в выставленную границу.

## Что сворачивается

Из истории (модельный контекст, не файл сессии):

```
[system] [brief?] M1 M2 ... M(n-K) | M(n-K+1) ... Mn
            └─────┬─────┘  └──── не трогать ────┘
           переносится как есть   (срезается и допишется в brief)
```

- **Не трогается**: system prompt, последний бриф (если есть), последние
  `keep_last_messages` сообщений (дефолт 10; для ручного — аргумент gRPC).
  «Сообщение» — сообщение с его tool_calls и связанными tool-результатами:
  срез никогда не разрывает пару assistant(tool_calls) ↔ tool — граница
  сдвигается вперёд до полной группы (правило cut point из pi).
- **Сворачивается**: всё **после** брифа (если его нет — с начала) до точки
  среза.
- **Бриф — не сворачивается**. Он передаётся в суммаризатор как есть, и
  модель обновляет его: дописывает в `Done`, пересобирает `State`/`Next`,
  `Task` не трогает, если пользователь его не менял. Повторное сжатие
  резюме-в-резюме (главный источник потери сути) исключено.

## Как сворачивается

Отдельный LLM-вызов (не часть рана), тот же endpoint:

```
max_tokens: 3000, enable_thinking: false, tools: []
system:  "You maintain the rolling state brief of a coding agent. ... "
         "разделы: ## Task (цель, 1–3 предложения) / ## Done (решения, "
         "файлы, команды, ошибки — старые пункты сохраняются, новые "
         "дописываются) / ## State (текущее состояние) / ## Next "
         "(оставшиеся шаги). Только факты, без воды, языком пользователя."
user:    "Previous brief: <старый бриф как есть, или (none — first compaction)>
         Conversation since the last brief (N messages):
         <только новые сообщения: роль + текст, tool-результаты обрезаны до 800 символов>"
```

- Суммарный ввод компакта ограничен `B` (если транскрипт больше ~120K символов —
  обрезается хвост транскрипта). Ввод включает предыдущий бриф, а он ограничен
  `max_tokens` самого компакта, так что размер брифа устойчив и не разрастается
  бесконечно.
- `length` на compact-запросе → `max_tokens` поднимается до 4000, один повтор.
- LLM-ошибка на compact-запросе → `compact_done` с `ok:false` (ран не рвётся,
  если это авто-путь, догоняет следующий триггер; на overflow-пути — один
  повторный compact через ~3 c: типичная причина сбоя — GPU-OOM в mtplx,
  движок «shed caches» и остаётся жив, память освобождается).
- SSE: `compact_started` → (LLM-вызов, его дельты идут в `compact_delta`) → `compact_done`.

## Результат в истории

```
[system]
[user]  "[Context compacted — rolling brief of the earlier conversation]"
        "## Task ... ## Done ... ## State ... ## Next ..."
[... последние K сообщений, без изменений]
```

- Оригинальные сообщения **не удаляются** из файла сессии (JSONL,
  см. план фазы 6): компакт — это вставка summary-entry, модельный
  контекст перестраивается с неё (как в pi). Это даёт возможность
  в будущем «отмотаться» и отфоркать до компакта.
- После компакта следующий обычный запрос принесёт свежий `P`;
  если `P + O ≤ B` — цикл продолжается.

## Ручной компакт

`Compact(keep_last_messages)` — то же самое без условия по токенам.
Используется, когда: пользователь видит в SSE, что `usage.prompt_tokens`
ползёт к границе и хочет сбросить заранее; или после смены цели (новая
большая задача). Если ран активен — компакт ставится на выполнение
после конца текущего turn'а, gRPC `CompactReply` вернётся, когда он
действительно сделан (блокирующий вызов, timeout 60 c).

## Тесты (критерий готовности фазы 5)

1. Наполнить историю фикстурой до `P + O > B` → на следующем turn'е
   `compact_started` с `reason:"auto"`, после компакта `P` падает ниже `B − O`.
2. Три подряд компакта в длинной сессии — бриф обновляется кумулятивно
   (раздел `Task` стабилен, `Done` растёт), агент помнит цель сессии
   (проверка по его финальному ответу).
3. Ручной `Compact` с активным раном — выполняется после turn'а, ран не рвётся.
4. `CONTEXT_OVERFLOW` не возникает ни при одном сценарии (инвариант из таблицы).
